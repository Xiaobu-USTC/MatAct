# MatAct

Code and data for **Learning reliable and cost-aware scientific tool use from executable experience**.

MatAct trains language-model agents to operate scientific software from executable experience.
Trajectories from expert workflows, agent logs, failure–repair traces and synthetic executions are
normalized, verified and utility-filtered. A policy is first trained with action-weighted supervised
fine-tuning, then optimized with GRPO against scientific verifiers and execution cost, and finally
improved by utility-filtered self-training in the environment where it is deployed. A scientific domain
enters only through its tool registry and its verifiers.

This repository holds the MatAct-specific code: the scientific tool environment, the MatAct-Bench task
generator, the trajectory construction pipeline, the verifiers and rewards, the action-weighted SFT
loss, the adapters for the RL framework, the runtime validator and the evaluation harness. Model
optimization runs on existing open-source frameworks (Hugging Face Transformers with DeepSpeed, verl,
vLLM and LLaMA-Factory); [Training](#training) lists which framework is used for which stage.

## Installation

The environment, task generator, trajectory pipeline, verifiers and evaluation harness use only the
Python standard library (Python 3.9 or later). NumPy speeds up geometry checks when it is installed.

```bash
git clone https://github.com/Xiaobu-USTC/MatAct.git && cd MatAct
pip install -e .            # core (no dependencies)
pip install -e ".[train]"   # stage 1: torch, transformers, accelerate, deepspeed
pip install -e ".[rl]"      # stage 2: verl, pandas, pyarrow
pip install vllm            # serving checkpoints for evaluation and self-training
```

The paper used Ubuntu 22.04, Python 3.10, PyTorch 2.4.0 and Transformers 4.51 on 8 × NVIDIA A100 80GB.

## Quick start

```bash
python scripts/build_dataset.py --out data   # about 20 s on a laptop CPU, writes about 190 MB
python -m unittest discover -s tests
python scripts/evaluate.py --suite test ood_chem tool_failure --policy expert
python scripts/evaluate.py --suite test --policy agent_emulator
```

The build is deterministic: the same `--seed` produces byte-identical files. The scripted expert
solves every task (SR 100% on all suites), and the agent emulator, which adds invalid and redundant
calls and careless settings, reaches SR 92.25% on the ID test set. These reference policies check the
installation and the harness; they are not model results.

### MatAct-Bench

| Category | Workflow | Task types (`subtype`) |
| --- | --- | --- |
| T1 `structure` | retrieval, validation, conversion, supercells, repair of uploaded files | `retrieve_convert`, `file_convert`, `repair_convert`, `density_compare`, `retrieve_missing` |
| T2 `first_principles` | DFT preparation, execution with repair, extraction | `dft_property`, `dft_singlepoint`, `dft_scf_repair`, `dft_mismatch`, `dft_missing` |
| T3 `ml_potential` | dataset split, potential selection, fine-tuning with repair, evaluation | `mlp_finetune`, `mlp_pretrained`, `mlp_unstable_repair`, `mlp_compare`, `mlp_missing` |
| T4 `database` | lookup, filtering, insertion with read-back, schema repair | `db_lookup`, `db_filter`, `db_insert`, `db_insert_two`, `db_insert_repair`, `db_missing` |

Every ID split follows the difficulty strata of Supplementary Table 2: 50% regular, 20% missing data,
15% tool failure and 15% long horizon. The 110 library entries are split by composition into 66
training, 11 validation, 18 test and 15 OOD-chem entries. Training tasks use training materials only,
and synthetic seed tasks that touch validation, test or OOD materials, or repeat a protected query or
task signature, are removed before any trajectory is kept.

```json
 "query": "Using qe-7.2 and the MatAct Tier-B protocol (...), compute the relaxed lattice constant a of fcc Au ...",
 "query_variants": {"formal": "...", "terse": "...", "novice": "...", "mixed": "..."},
 "params": {"formula": "Au", "prototype": "fcc", "property": "lattice_a_A", "unit": "Å"},
 "initial_state": {"workspace": {}, "available_models": ["qe-7.2", "chgnet-0.3", "mace-mp-medium"],
                   "resource_budget": {"cpu_hours": 12.0, "gpu_hours": 0.0}},
 "available_tools": ["structure.search", "structure.load", "structure.validate", "dft.prepare",
                     "dft.run", "result.extract", "artifact.inspect"],
 "success_spec": {"deliverables": ["lattice_a_A", "output URI"], "must_be_grounded": true},

```

The policy sees only `query` and the `<environment_state>` built from `initial_state` and
`available_tools`. `params` (read by the scripted workflows), `faults` and `reference` stay hidden.

### Seed trajectory pool

The released pool follows the inventory of Supplementary Table 3:

| Source | Raw | Retained | Keep rate |
| --- | ---: | ---: | ---: |
| Expert workflows | 1,500 | 1,260 | 84.0% |
| Historical agent logs | 2,000 | 1,180 | 59.0% |
| Failure–repair traces | 1,200 | 840 | 70.0% |
| Synthetic executions | 2,400 | 1,620 | 67.5% |
| **Total** | **7,100** | **4,900** | **69.0%** |

The retained trajectories keep the composition 25.7%, 24.1%, 17.1% and 33.1% from the four sources.
Expert workflows and agent logs are recorded by running the repository's policy library on training
tasks (`pipeline/sources.py`) and are written as they were recorded, with whatever defects the sessions
contained (legacy tool names from older agent stacks, multi-action messages, interrupted or corrupted
recordings, unsupported claims). Failure–repair traces are recorded on the tool-failure tasks and on
fault-injected copies of regular tasks; synthetic executions are recorded on newly generated tasks
that pass the leakage control below. All sources are then sampled with a fixed seed to the inventory
above, so the released counts match the published ones.

Raw traces go through the ordered normalization rules of Supplementary Note 4
(`pipeline/normalize.py`): legacy tool and argument names are mapped to the registry, multi-action
messages are split when the number of calls matches the number of observations, observations are kept
verbatim and failure–repair edges are attached. Each normalized trace is then replayed in a fresh
environment (`pipeline/quality.py`). Traces are rejected when the logged observations differ from the
replay, or when they contain malformed calls, citations of non-existent artifacts, untraceable numbers
or failed task checks. The remaining traces need a utility Q(τ) ≥ γ_cold = 0.72; among exact
duplicates, the trace with the highest utility, then the lowest cost, then the shortest horizon is
kept. `seed/qc_report.jsonl` records the outcome for every raw trace.

An SFT record from `sft/train_messages.jsonl` (system prompt, state and some fields abridged):

```text
[system]    You are MatAct, a materials-computing agent operating in a typed scientific software environment. ...
[user]      Register the computed result in workspace://results/calc_0066_1.json in the user database
            (matact_userdb) and verify that the record was written correctly.
            <environment_state> {...} </environment_state>
[assistant] Read the computed result and its metadata.
            <tool_call>
            {"name": "artifact.inspect", "arguments": {"uri": "workspace://results/calc_0066_1.json"}}
            </tool_call>
[tool]      {"observation_id": "obs-1", "status": "success", "type": "calc_result", "formula": "SrS", ...}
[assistant] Insert the energy_per_atom_eV record for SrS with the result file as provenance.
            <tool_call> {"name": "database.update", "arguments": {...}} </tool_call>
[tool]      {"observation_id": "obs-2", "status": "error", "code": "SCHEMA_CONFLICT",
             "message": "collection policy requires the field 'calc_type'"}
[assistant] The collection requires calc_type; add it from the result file and retry.
            <tool_call> {"name": "database.update", "arguments": {...}} </tool_call>
[tool]      {"observation_id": "obs-3", "status": "success", "record_uri": "...", "receipt_uri": "..."}
[assistant] Read the written record(s) back to verify them.
            <tool_call> {"name": "database.query", "arguments": {...}} </tool_call>
[tool]      {"observation_id": "obs-4", "status": "success", "n_records": 1, ...}
[assistant] The writes are confirmed by receipts and a read-back query.
            <answer>
            Inserted into matact_userdb: SrS (mx-0080) energy_per_atom_eV = -6.5159 eV/atom (receipt
            workspace://database/transactions/tx-001.json, ...). Reading them back (...) returns 1 record(s)
            with the same values.
            </answer>
```

Every record also carries `tools`, the JSON schemas of all 14 registry tools in OpenAI function
format, which the chat template renders into the system prompt. The tools that a task provides are
listed in `<environment_state>` (policy rule 1). Assistant turns hold an optional short rationale and
one `<tool_call>` or one `<answer>` block; tool turns hold the JSON observation, which is masked in the
loss. RL rows (`rl/*.jsonl`) follow the verl format: `prompt` holds the system and user messages,
`reward_model.ground_truth` the full task and `extra_info.tools_kwargs` the environment specification
from which each rollout's environment is created.

## Environment

| Tool | Family | Cost | Output | Typical failure |
| --- | --- | ---: | --- | --- |
| `structure.search` | structure | 1 | candidate IDs and metadata | no match |
| `structure.load` | structure | 1 | CIF/XYZ/POSCAR object | missing path |
| `structure.validate` | structure | 1 | canonical structure + warnings | invalid geometry |
| `structure.convert` | structure | 1 | converted structure file | unsupported format |
| `dft.prepare` | first principles | 2 | input directory | invalid parameter |
| `dft.run` | first principles | 8 | status and output URI | timeout/non-convergence |
| `result.extract` | first principles | 2 | scalar/vector properties | missing field |
| `mlp.select` | ML potential | 2 | model handle | incompatible cutoff |
| `mlp.train` | ML potential | 7 | model artifact + logs | unstable training |
| `mlp.evaluate` | ML potential | 3 | MAE/RMSE | shape mismatch |
| `database.query` | database | 1 | records and provenance | empty result |
| `database.update` | database | 2 | transaction receipt | schema conflict |
| `artifact.inspect` | utility | 1 | metadata/checksum | stale artifact |
| `code.execute` | utility | 4 | stdout/stderr + files | runtime exception |

How the executors behave:

- **Structures.** `matact/chem` parses and writes CIF (P1), POSCAR and extended XYZ. Validation checks interatomic distances and reports the density; conversion supports supercells and merging of duplicated sites.
- **First principles.** `dft.prepare` checks the parameters and estimates CPU hours from the number of atoms, k-points, cutoff and relaxation. `dft.run` charges the CPU budget, times out when `max_cpu_hours` is too low and fails to converge for metals without smearing, or under an injected charge-sloshing fault until `mixing_beta` ≤ 0.3. Extracted values equal the reference values plus errors that grow with a low cutoff, a coarse k-point mesh or strain, so only settings that follow the Tier-B protocol (cutoff ≥ 520 eV, k-point spacing ≤ 0.15 Å⁻¹, i.e. nᵢaᵢ ≥ 2π/0.15 ≈ 42 Å, and smearing for metals) reproduce the reference within tolerance.
- **ML potentials.** `mlp.select` returns the cheapest registered potential that supports the elements and the task. The fine-tuning error depends on the data size, the number of epochs and the chemical system, and evaluating on training structures is detected and flagged.
- **Databases.** `matact_refdb` is read-only and covers 80% of the library in environment v1. `matact_userdb` accepts schema-checked records whose `source_uri` must point to an existing artifact.
- **Utilities.** `artifact.inspect` returns metadata and checksums or lists a directory; `code.execute` runs two registered scripts, `split_dataset` and `convert_units`.

**Environment versions.** v1 is the default. v2 is the scheduled update used in the environment-shift
experiment: full database coverage with structure URIs in the records, a new fine-tuned potential
(`mace-ft-matact-v2`, cheaper and more accurate) and the deprecation of `structure.search`.

**Errors.** Every failed call returns a typed code (for example `MISSING_ARTIFACT`, `NON_CONVERGENCE`
or `BUDGET_EXCEEDED`) that `env/common.py` maps to the failure labels of Supplementary Table 8.

**Using real backends.** Each tool is a method `_t_<family>_<name>` (for example `_t_dft_run`) in
`matact/env/handlers_*.py` that receives schema-checked arguments and returns an observation
dictionary. A handler can call real software, such as ASE with Quantum ESPRESSO for `dft.run` or MACE
for `mlp.evaluate`, as long as it returns the same observation fields. The reference values in
`matact/env/materials.py` and in the task builders must then be recomputed with the same backend.

## Verifiers, utility and reward

Verifiers run in the order of Supplementary Note 7: parser, schema, availability, preconditions,
execution, artifact, scientific consistency, grounding and cost. Task success (`verify/checks.py`) is
decided by category-specific checks on the final environment state:

| Check | Passes when |
| --- | --- |
| structure artifact (T1) | a converted file with the requested format, composition and atom count exists, is cited and has no overlapping sites |
| DFT value (T2) | the reported value is within the Tier-B tolerance (0.5% for lattice constants, 2 meV/atom for energies, 0.05 eV for band gaps), the cited output exists and its settings follow the protocol |
| ML potential (T3) | a held-out split exists, the model was trained on the training split only and its held-out errors are reported and cited |
| database (T4) | values match the record within 1% and cite it, ID lists match exactly, and writes exist and are read back after the last write |
| missing data | the answer reports the missing resource, cites the failed observation and substitutes no other structure, record or dataset |

Grounding requires every number in the final answer to be traceable to the query, the issued
arguments or an observation; unit conversions and differences or ratios of observed values are
allowed. Citing an artifact URI or observation ID that does not exist sets R_ground to 0. All checks
are programmatic. The semantic-judge prompt is included in `protocol.py`, but no task in this release
needs it.

Utility (Supplementary Eq. S2, `verify/scoring.py`; 0.90 when every term is 1 and the cost penalty is 0):

    Q(τ) = 0.30 R_task + 0.25 R_exec + 0.20 R_sci + 0.15 R_ground − 0.10 C(τ)

- R_task: fraction of task checks passed (0 without a final answer).
- R_exec: fraction of calls that executed. A failed call counts only if the task forces that error (the scripted expert meets it too) and a later call of the same tool family succeeds; empty results count as executed.
- R_sci: protocol, geometry and held-out-split checks.
- R_ground: 0.5 × (the answer cites an existing artifact or observation) + 0.5 × provenance traceability.
- C(τ) = 0.6 min(1, cost/cost_expert − 1) + 0.2 min(1, 3 redundant/n) + 0.2 min(1, 2 failed/n) for n calls, with the registry cost units and the cost of the scripted expert on the same task.

Reward for GRPO (Supplementary Eq. S3), clipped to [−1, 1], where FCR_τ is the share of well-formed
calls in the trajectory:

    R(τ) = 0.40 (0.6 R_task + 0.4 R_sci) + 0.25 R_exec + 0.25 (0.5 FCR_τ + 0.5 R_ground) − 0.10 C(τ)

## Training

MatAct does not ship its own trainer. Each stage runs on an existing framework, and MatAct supplies
the data, the loss, the tools and the rewards:

| Stage | Framework | MatAct code |
| --- | --- | --- |
| 1. Action-weighted SFT | Hugging Face Transformers `Trainer` + DeepSpeed ZeRO-3 | token classes and weighted loss: `matact/train/weighted_sft.py` |
| Standard SFT (baseline) | LLaMA-Factory, or `weighted_sft.py --uniform` | ShareGPT export: `data/sft/sft_sharegpt.jsonl` |
| 2. Verifiable, cost-aware GRPO | verl (GRPO with SGLang multi-turn rollouts) | tools: `integrations/verl_tools.py`; reward: `integrations/verl_reward.py` |
| 3. Self-training rollouts | vLLM (OpenAI-compatible server) | `agents/llm.py`, `pipeline/selftrain.py`, `scripts/self_train.py` |
| Evaluation | vLLM | `scripts/evaluate.py`, `matact/eval/` |

Hyperparameters follow Supplementary Table 6 (Qwen3-8B, full-parameter): AdamW (β = 0.9, 0.95),
weight decay 0.1, warm-up ratio 0.03, cosine schedule, global batch 64 (8 GPUs × 1 sequence × 8
accumulation steps) and maximum length 4,900 tokens. SFT runs 3 epochs at 1e-5; GRPO runs 1 epoch at
1e-6 with 8 rollouts per prompt, temperature 1.0, top-p 1.0, clip 0.2 and KL coefficient 0.02; the two
self-training rounds use 5e-7. The paper reports three runs with seeds 13, 42 and 3407.

### Stage 1: action-weighted SFT

| Token class | Weight |
| --- | ---: |
| tool name, `<tool_call>` and `<answer>` boundaries | 2.5 |
| argument keys and values, grounded answer | 2.0 |
| user request, end-of-turn token | 1.0 |
| rationale | 0.5 |
| system prompt, observations, padding, truncated suffix | 0 (masked) |

```bash
MODEL=Qwen/Qwen3-8B OUT=outputs/qwen3-8b-awsft SEED=42 bash scripts/train_awsft.sh
bash scripts/train_awsft.sh --uniform                           # standard SFT baseline
llamafactory-cli train configs/llamafactory_sft_qwen3_8b.yaml  # standard SFT baseline with LLaMA-Factory
```

Conversations are rendered with the model's own chat template, with the full tool registry passed as
`tools`. The empty `<think>` block that Qwen3 templates add before the last turn is removed, so every
turn has the layout that the default template produces at inference; serve the trained checkpoints
with the default chat template. The loss is normalized over the non-masked tokens of each micro-batch.

### Stage 2: verifiable, cost-aware GRPO with verl

```bash
MODEL=outputs/qwen3-8b-awsft bash scripts/train_grpo_verl.sh
REWARD_FN=compute_score_generic EXP_NAME=generic-toolrl MODEL=<sft-checkpoint> bash scripts/train_grpo_verl.sh
```

The second command trains the generic tool-RL baseline, whose reward uses formatting, execution
success and final-answer correctness only. During a rollout, `MatActTool` executes the policy's calls
in one environment per rollout; afterwards `compute_score` parses the response, replays its actions in
a fresh environment and returns R(τ). The script uses the configuration keys of recent verl releases,
which may need adjusting for the installed version. Convert the saved actor checkpoint to Hugging Face
format with verl's model merger before serving it.

### Stage 3: environment-grounded self-training

One round (Supplementary Algorithm 1) rolls out eight candidates per training task with the current
policy, keeps candidates that pass the verifiers with Q(τ) ≥ γ_self = 0.78, removes duplicates by tool
sequence and answer similarity, fine-tunes for one epoch on D_cold ∪ D_repair ∪ Filter(D_self) and
then applies GRPO again:

```bash
vllm serve outputs/qwen3-8b-grpo --served-model-name matact --enable-auto-tool-choice --tool-call-parser hermes
python scripts/self_train.py --model matact --temperature 1.0 --candidates 8 --out data/self_train/round1
MODEL=outputs/qwen3-8b-grpo TRAIN_FILE=data/self_train/round1/train_messages.jsonl EPOCHS=1 LR=5e-7 \
  OUT=outputs/round1-sft bash scripts/train_awsft.sh
MODEL=outputs/round1-sft LR=5e-7 EXP_NAME=round1-grpo bash scripts/train_grpo_verl.sh
```

Repeat these steps for the second round. For the environment-shift experiment, run one more round
with `--tasks data/benchmark/env_shift_train.jsonl` (environment v2, training materials) and evaluate
on `env_shift`. `--threshold -1` keeps every candidate that passes the hard filters (the ablation
without utility filtering), and `--no-cold` writes only the filtered rollouts, for example
trajectories of an external teacher model served behind the same API for the trajectory-budget
experiment.

## Evaluation

```bash
vllm serve outputs/qwen3-8b-matact --served-model-name matact --enable-auto-tool-choice --tool-call-parser hermes
python scripts/evaluate.py --policy openai --model matact \
  --suite test ood_chem ood_comp paraphrase tool_failure env_shift --out results/matact_s42.json
python scripts/evaluate.py --policy openai --model matact --suite stress --validator rule \
  --out results/matact_validator.json
python scripts/compare.py --a results/matact_s13.trajectories.jsonl results/matact_s42.trajectories.jsonl \
  --b results/sft_s13.trajectories.jsonl results/sft_s42.trajectories.jsonl --metric success
```

For an untrained Qwen3 model, add `--chat-template-kwargs '{"enable_thinking": false}'` to evaluate
it in non-thinking mode. `--reference results/<agent>.json` normalizes CPS to the result file of
another agent. Each run writes the metrics (JSON) and every trajectory with its scores
(`*.trajectories.jsonl`).

| Metric | Definition in this release |
| --- | --- |
| SR | tasks whose category checks all pass and that end with a final answer (%) |
| FR | answers that agree with the reference or are directly supported by observations, without untraceable numbers or unknown citations (%) |
| FCR | policy turns that parse, name a registered tool, satisfy its schema and use workspace paths (%) |
| ESR | executed calls without argument, availability, precondition, execution, artifact or cost errors (%) |
| ATC | mean tool calls per task, successful and failed |
| CPS | registry cost units of all calls divided by the number of successful tasks |
| PT | numbers in the answer that are traceable to evidence (%) |

The runtime validator (`--validator rule`, or `--validator llm --validator-model <name>` for a
prompted model as in the paper) checks each proposed action before execution. The router executes
accepted actions, executes repaired actions in place of the original, returns rejections to the policy
as observations, asks the policy to re-issue high-risk actions before running them and ends the
episode after three consecutive rejections. Validator calls are not counted in ATC or CPS.
`compare.py` averages per-task outcomes over runs and reports two-sided paired permutation tests
(10,000 permutations), Holm–Bonferroni-adjusted p-values and task-level bootstrap 95% confidence
intervals.
